# 契约重构 v1：表 / 实体 / 查询

> 范围：`contracts/_meta/data.{tables,entities,queries}.yaml`、`contracts/data/{storage.yaml,tables,entities,queries}`、`scripts/cmd/internal/{check,graph,contractspec}`。
> 状态：已落地；`make contract-check`、`make gen-graph-check`、`make test-tools`、`make lint-tools`、`make test-api`、`scripts/check-docs.sh` 全部通过。

---

## 1. 目标与原则

契约是**接口**，不是实现。只写硬约束、确定性事实和明确结果：

1. **单一真相源**：同一事实只在一个层声明，其他层引用或派生。
2. **派生语法，声明语义**：名称/类型/校验/描述等机械事实从来源列派生；枚举映射、关系、computed、多表组合等语义必须显式。
3. **可脚本校验**：checker 能验证的才写进硬规则；SQL 执行细节不写进契约。
4. **AI 可读**：字段名、引用、`do_not`/`caution` 直接面向生成；不依赖隐式命名猜测。

---

## 2. 表：物理事实

- `table.extends` 是唯一继承入口；`_base` 提供 5 个基础列。
- `engine / size_class / retention / partition` 在 `contracts/data/storage.yaml` 的 `tables` 注册表；表契约只写业务结构。
- 列声明类型、可空、约束、索引、冗余、`pii`/`never_expose`、`comment`；这些是 entity 派生的事实源。
- 反向映射：`table.entities`、`model.included_by` 显式声明并由 checker 校验；`used_by.queries` 由 `make gen-graph` 写回。

**表契约回答**：数据物理上是什么。**不回答**：如何被访问、以什么形状暴露。

---

## 3. 实体：读模型与表映射

### 3.1 表 ↔ 实体是多对多

- 一个实体可映射多张表：`model.tables` 列表，第一个是主表。
- 一张表可被多个实体映射：反向 `table.entities` 显式列出，checker 校验。
- 多表实体的字段用 `source.column` 明确指向具体表；单表实体同样显式写来源。
- 每个标量字段必须有 `source.column` 或 `source.computed`，二选一。

### 3.2 只写语义增量

字段的机械事实从来源列派生，**不需要重复写**：

| 字段属性 | 默认来源 | 何时显式写 |
|---|---|---|
| `json_name` | `snake_case(name)` | 消费侧要改名 |
| `type` | 列类型 + `nullable`（可空加 `*`） | 枚举映射、computed、显式覆盖 |
| `validation` | `{ column: source.column }` | 需要 pattern/soft 或跨列校验 |
| `description` | 列 `comment` | 消费侧措辞不同 |
| `pii` / `never_expose` | 来源列标记 | 只能收紧，不能放松 |
| `mutable` | `true`；computed 默认 `false` | 业务只读字段 |

仍必须显式：

- `name`（Go 字段名）；
- `target`（表）/ `type`（entity）/ `join_column_from` / `join_column_to` / `load`（关系）；
- `type: data.enums.*`（枚举映射，列必须是 integer）；
- `computed` + `type`（计算/聚合字段，必须 `*T`、`mutable:false`、不得引用 `@param`）；
- 关系字段的 `description`；
- 收紧敏感标记或改写描述时。

### 3.3 关系

```yaml
- name: Tokens
  target: data.tables.token
  type: data.entities.token
  join_column_from: data.tables.account.col.id
  join_column_to: data.tables.token.col.account_id
  load: lazy
  description: "账号的设备令牌"
```

- 基数由两端列唯一性推断：两端唯一 one_to_one；from 唯一 one_to_many；to 唯一 many_to_one；两端都不唯一不允许。
- `join_column_from` 与 `join_column_to` 类型族必须一致；eager 的 `join_column_to` 必须有索引且不得成环。
- 关系不写 `source`/`type`/`validation`/`mutable`/`pii`/`never_expose`/`examples`。

### 3.4 校验与敏感

- `validation` 显式时三选一：`column`（复用列规则）、`pattern`（string 硬正则）、`soft`（脚本无法验证的表达式）。
- 跨字段校验写在实体顶层 `validation`，不写 DDL。
- `pii` / `never_expose` 从列继承；显式 `false` 不能覆盖列为 `true`；`never_expose` 字段名必须小写开头。

## 4. 查询：接口契约

查询只声明**入参、结果、目标表与索引引用**；item 不写 id（项 ID 由文件 ID + name 派生）；读写归属在 capabilities 层；SQL 如何执行由实现负责。

```yaml
- name: ListAccounts
  targets: [ data.tables.account ]
  params:
    - { name: status, type: integer, column: data.tables.account.col.status, nullable: true }
    - { name: page_size, type: integer, default: 20 }
  returns: List<data.entities.account>
  index_ref:
    - data.tables.account.idx_accounts_created_at_id
    - data.tables.account.idx_accounts_own_type_own_id
```

| 字段 | 含义 | 硬约束 |
|---|---|---|
| `returns` 基数 | `List<T>` / 非列表 / `affected_rows` | `List<T>` 是列表；`affected_rows` 是写语句结果；非列表是单条 |
| `targets` | 查询读写的表 | 存在、非 `data.tables.base`、去重 |
| `params` | 接口入参 | name 唯一、type 非空；`column` 绑定后类型族必须与列一致 |
| `returns` 类型 | 表行 / 实体 / 标量 / `object` | 引用的表/实体必须存在；object 必须配 `output_fields` |
| `return_columns` | 结果投影 | 只能是表行/实体；敏感列只有同模块可显式列出 |
| `output_fields` | object 的字段清单 | 只写 `name`/`type`；name 唯一、type 非空 |
| `index_ref` | 查询依赖的索引 | 指向 PK 或 `indexes[].name`；单表至少一个；与 `used_by` 双向 |

**不写**：`statement`、`where`、`order_by`、`limit`、`values`、`expr`、`joins`、`semantics`。这些是 SQL 实现细节，写进契约会制造第二份真相，且 checker 无法验证 SQL 语义。

`index_ref` 是设计声明：checker 保证索引存在、属于目标表、与 `used_by` 一致；是否真正命中由 `EXPLAIN` 验证。

改名过渡用 `previous_names`：旧 `name` 派生的 ID 会解析到当前查询；消费者迁移后删除。读写归属移到 capabilities：service 用 `persistence.write_queries`，async 用 `writes`，checker 校验登记、单表与模块归属。

## 5. 单一真相源矩阵

| 事实 | 唯一来源 | 其他层如何获得 |
|---|---|---|
| 列类型/可空/约束/注释/pii | table 列 | entity 默认派生；query 通过 `params.column`/`returns` 引用 |
| 索引 | table `indexes` | query `index_ref` 引用；`used_by` 双向校验 |
| 表归属 | table `owner_module` | capabilities `write_queries` / `writes` 校验 |
| 枚举码 | `data/enums.yaml` | entity `type: data.enums.*` 映射 |
| 关系 | entity `fields` | target entity 的 `model.included_by` 显式，checker 校验 |
| 表↔实体多对多 | entity `model.tables` + 字段 `source.column` | table `table.entities` 显式，checker 校验 |
| 查询入参/结果 | query `params`/`returns` | 生成方法签名与测试骨架 |
| 业务校验 | entity `validation` | 生成校验骨架 |

## 6. 硬约束与软区

**checker 硬校验**：ID/名称/键顺序、表/列/索引/实体引用、owner、返回形状、参数列类型、返回投影、敏感列、关系方向/类型/eager、`used_by` 对账、capabilities 写查询登记、storage 登记。

**仍是软区**：

1. `source.computed` 只校验非空、`*T`、不引用 `@param`；表达式引用哪些列无法脚本化。
2. 查询 SQL 不在契约内：参数是否被 SQL 使用、索引是否真正命中、过滤/排序语义，需要实现测试与 `EXPLAIN`。
3. `description` / `do_not` / `caution` 是 AI 语义提示，不是机器规则。
4. `return_columns` 按物理列名，不按实体字段名/JSON 名。
