# 契约重构 v1：表 / 实体 / 查询

> 范围：`contracts/_meta/{_types.yaml,data.{tables,entities,queries}.yaml}`、`contracts/data/{storage.yaml,redundancy.yaml,tables,entities,queries}`、`scripts/cmd/internal/{check,graph,contractspec}`。
> 状态：已落地；`make contract-check`、`make gen-graph-check`、`make test-tools`、`make lint-tools`、`make build-api`、`make test-api`、`scripts/check-docs.sh` 全部通过。

---

## 1. 目标与原则

契约是**接口**，不是实现。只写硬约束、确定性事实和明确结果：

1. **单一真相源**：同一事实只在一个层声明，其他层引用或派生。
2. **派生语法，声明语义**：名称/类型/校验/描述等机械事实从来源列派生；枚举映射、关系、computed、多表组合等语义必须显式。
3. **可脚本校验**：checker 能验证的才写进硬规则；SQL 执行细节不写进契约。
4. **AI 可读**：字段名、引用、`do_not`/`caution` 直接面向生成；不依赖隐式命名猜测。

## 2. 表：物理事实

- `table.extends` 是唯一继承入口；`_base` 提供 5 个基础列。
- `engine / size_class / retention / partition` 在 `contracts/data/storage.yaml` 的 `tables` 注册表（engine 必填）；跨表冗余组在 `data/redundancy.yaml` 的 `groups`；表契约只写业务结构。
- 类型族（string/integer/timestamp/...）统一在 `contracts/_meta/_types.yaml`，tables/entities/queries 共用；`columns[].type` 的 `data.tables.<t>.col.<c>` 引用规则硬编码在 checker，不是外键。
- 列声明类型、可空、CHECK、索引、冗余组 ID、`sensitivity`、`comment`；这些是 entity 派生的事实源。
- 唯一性统一由 `indexes[].unique` 表达：`live_only: true` 只约束未软删行，`false`/省略约束全表（含软删行）。
- 索引只保留 `name/columns/expression/unique/live_only/comment/used_by`；`method` / `concurrently` / `include` 已移除，迁移并发策略归运行时迁移配置。
- 反向映射：`table.entities`、`model.included_by` 显式声明并由 checker 校验；entity 的 `used_by.queries` / `used_by.capabilities` 由 `make gen-graph` 写回。

**表契约回答**：数据物理上是什么。**不回答**：如何被访问、以什么形状暴露。

### 2.1 本轮取舍

| 项 | 结论 | 理由 |
|---|---|---|
| `column_types` | 拆到 `_meta/_types.yaml` | tables/entities/queries 共用同一套值类型；避免非表契约依赖表规范 |
| `column_refs` | 删除，规则硬编码 | `columns[].type` 只允许 `data.tables.<t>.col.<c>`，不再维护可配置前缀 |
| `pii` / `never_expose` | 合并为 `sensitivity: public\|pii\|secret` | 减少两个布尔值的组合歧义；`pii` 可脱敏返回，`secret` 禁止返回 |
| `constraints.unique` | 删除 | 唯一性只由索引表达，避免两套唯一性语义 |
| `constraints.exclude` | 删除 | 当前 0 使用，且 `expr` 无法脚本校验；只保留 `check` |
| `constraints[].columns` | 删除 | CHECK 已统一用 `expr` |
| 索引 `method/concurrently/include` | 删除 | 当前 0 处使用；迁移并发策略归运行时迁移配置 |
| 索引 `reason` | 改名 `comment` | 与表/列注释统一，生成 `COMMENT ON INDEX` |
| 冗余组 | 明细移到 `data/redundancy.yaml` 的 `groups` | 表列只保留组 ID，跨表 source/copies 集中登记，checker 双向校验 |

## 3. 实体：读模型与表映射

### 3.1 表 ↔ 实体是多对多

- 一个实体可映射多张表：`model.tables` 列表，第一个是主表。
- 一张表可被多个实体映射：反向 `table.entities` 显式列出，checker 校验。
- 多表实体的字段用 `source.column` 明确指向具体表；单表实体同样显式写来源。
- `entities/_base` 的 5 个字段类型从 `tables/_base` 继承，不在实体基类重写；具体实体特化 `Status` 时必须放在 `fields` 第一项。
- 每个标量字段必须显式 `source`，三选一：`column` / `computed` / `soft`；不得同时写多个。

### 3.2 只写语义增量

标量字段必须显式 `description` / `source` / `validation`；其余机械事实才可派生：

| 字段属性 | 默认来源 | 何时显式写 |
|---|---|---|
| `json_name` | `snake_case(name)` | 消费侧要改名 |
| `type` | 列类型 + `nullable`（可空加 `*`） | 枚举映射、computed/soft、显式覆盖 |
| `sensitivity` | 来源列标记 | 只能收紧，不能放松；`pii` 可脱敏返回，`secret` 不得返回 |

仍必须显式：

- `name`（Go 字段名）；
- `description`（不从列 comment 继承）；
- `source`（三选一：`column` / `computed` / `soft`）；
- `validation`（三选一：`column` / `pattern` / `soft`；`column` 必须等于 `source.column`）；
- `type`（目标 entity）/ `join_column_from` / `join_column_to` / `load`（关系）；
- `type: data.enums.*`（枚举映射，列必须是 integer）；
- `computed` + `type`（计算/聚合字段，必须 `*T`、不得引用 `@param`）；
- `soft` + `type`（外部传入或无法脚本化的来源）。

### 3.3 关系

```yaml
- name: Tokens
  description: "账号的设备令牌"
  type: data.entities.token
  join_column_from: data.tables.account.col.id
  join_column_to: data.tables.token.col.account_id
  load: lazy
```

- 基数由两端列唯一性推断：两端唯一 one_to_one；from 唯一 one_to_many；to 唯一 many_to_one；两端都不唯一不允许。
- `join_column_from` 与 `join_column_to` 类型族必须一致；eager 的 `join_column_to` 必须有索引且不得成环。
- 关系不写 `source`/`validation`/`sensitivity`。

### 3.4 校验与敏感

- 标量字段的 `validation` 必填，三选一：`column`（复用列规则，必须等于 `source.column`）、`pattern`（string 硬正则）、`soft`（脚本无法验证的表达式）。
- 跨字段校验写在实体顶层 `validation`，item 用 `name` 而不是 `id`，ID 派生为 `<entity-id>.<name>`。
- `sensitivity` 从列继承；显式值不得低于来源列；`secret` 字段名必须小写开头。
- 三个级别：`public` 可返回；`pii` 允许脱敏后返回；`secret` 是禁止返回的硬门禁（密码哈希、令牌哈希）。

## 4. 查询：接口契约

查询只声明**入参、结果、目标表与索引引用**；item 不写 id（项 ID 由文件 ID + name 派生）；读写归属在 capabilities 层；SQL 如何执行由实现负责。

```yaml
- name: ListAccounts
  tables:
    - data.tables.account
  params:
    - { name: offset, type: integer, nullable: true, default: 0 }
    - { name: limit, type: integer, nullable: true, default: 20 }
    - { name: status, type: integer, column: data.tables.account.col.status, nullable: true }
    - { name: has_nickname, type: boolean, expr: "nickname IS NOT NULL" }
  returns:
    - { name: accounts, list: true, kind: entity, entity: data.entities.account }
  index_ref:
    - data.tables.account.idx_account_created_at_id
    - data.tables.account.idx_account_own_type_own_id
```

| 字段 | 含义 | 硬约束 |
|---|---|---|
| `returns[].kind` | `column` / `entity` / `table` / `scalar` / `affected_rows` | kind 专属字段必须出现，互斥字段不得出现 |
| `returns[].list` | 该项是否为列表 | 同一 query 的多项必须一致；`affected_rows` 不得为列表 |
| `return_columns` | 已合并进 `returns[].columns` | 只用于 `table` / `entity`；secret 只有同模块可显式列出 |
| `entity.columns` | 实体投影 | 省略表示默认投影；显式时必须覆盖全部非指针、非 secret 字段 |
| `tables` | 查询读写的表 | 存在、非 `data.tables.base`、去重；实例竖排 |
| `params.offset` | 分页起点 | list 返回必须声明；type=integer、nullable:true、default=0 |
| `params.limit` | 返回/批处理上限 | list 返回必须声明；type=integer、nullable:true、default 必须为正数 |
| `params` | 接口入参 | name 唯一、type 非空；`column` 绑定后类型族必须与列一致；`default` 只在 `nullable: true` 时允许 |
| `params.column` / `params.expr` | 参数绑定列或表达式 | 二者互斥；表达式只校验非空，SQL 语义由实现验证 |
| `index_ref` | 查询依赖的索引 | 指向 PK 或 `indexes[].name`；单表至少一个；与 `used_by` 双向 |

**不写**：`statement`、`where`、`order_by`、`values`、`joins`、`semantics`。这些是 SQL 实现细节，写进契约会制造第二份真相，且 checker 无法验证 SQL 语义；`params.expr` 只允许作为参数表达式存在，不承载整段 SQL。

`index_ref` 是设计声明：checker 保证索引存在、属于目标表、与 `used_by` 一致；是否真正命中由 `EXPLAIN` 验证。

`previous_names` 已移除：`name` 是稳定键，改名即新 ID。读写归属移到 capabilities：service 用 `persistence.write_queries`，async 用 `writes`，checker 校验登记、单表与模块归属。

## 5. 单一真相源矩阵

| 事实 | 唯一来源 | 其他层如何获得 |
|---|---|---|
| 值类型族 | `_meta/_types.yaml` | table/entity/query 共用；不再从 `data.tables` 取类型词表 |
| 列类型/可空/约束/注释/sensitivity | table 列 | entity 默认派生；query 通过 `params.column`/`returns` 引用 |
| 索引 | table `indexes` | query `index_ref` 引用；`used_by` 双向校验；唯一性统一由 `unique` 索引表达，`live_only` 决定作用域 |
| 冗余组 | `data/redundancy.yaml` 的 `groups` | 表列只写组 ID；checker 双向校验 source/copies 与 type/nullable |
| 表归属 | table `owner_module` | capabilities `write_queries` / `writes` 校验 |
| 枚举码 | `data/enums.yaml` | entity `type: data.enums.*` 映射 |
| 关系 | entity `fields` | `relation.type` 目标的 `model.included_by` 显式，checker 校验 |
| 表↔实体多对多 | entity `model.tables` + 字段 `source.column` | table `table.entities` 显式，checker 校验 |
| 查询入参/结果 | query `params`/`returns` | 生成方法签名与测试骨架 |
| 业务校验 | entity `validation` | 生成校验骨架 |

## 6. 硬约束与软区

**checker 硬校验**：ID/名称、字段顺序（tables/entities/queries/enums 均以 `_meta` 模板的 `fields`/`item_fields` 顺序为准，含嵌套对象）、表/列/索引/实体引用、owner、返回形状、参数列类型、返回投影、`secret` 投影、关系基数/类型/eager、`live_only` 依赖 `deleted_at`、唯一索引命名、`used_by` 对账、冗余组双向一致、capabilities 写查询登记、storage 登记。

**仍是软区**：

1. `source.computed` 只校验非空、`*T`、不引用 `@param`；`source.soft` 只校验非空；具体来源语义无法脚本化。
2. `CHECK expr` 只校验非空；SQL 语义由生成器/数据库验证，checker 不解析 SQL。
3. 查询 SQL 不在契约内：参数是否被 SQL 使用、索引是否真正命中、过滤/排序语义，需要实现测试与 `EXPLAIN`。
4. `description` / `do_not` / `caution` 是 AI 语义提示，不是机器规则。
5. `returns[].columns` 按物理列名，不按实体字段名/JSON 名。

## 9. 已知剩余项

- `index.yaml` 的 entity/query `enforcement` 仍标 `generated+tested`，但 `gen-db` / 查询生成器尚未实现；生成链落地前应按实际降级或补齐。
- `source.computed` / `source.soft`、SQL 语义、索引真实命中、实体字段描述属于软区，需要生成器测试/EXPLAIN/review 兜底。
- `returns[].columns` 仍按物理列名；如需按实体字段名，需统一生成器投影协议。
- storage `tables` 与表契约的双向登记是“物理事实集中”的成本，规模上来后收益更明显。
- `CHECK expr` 的 SQL 语义不在 checker 内；生成器/数据库验证前，它仍是“硬约束的声明 + 软验证”。
- `sensitivity` 的 `pii` 只表达“可脱敏返回”；具体脱敏算法由 API/序列化层实现，checker 不校验脱敏方式。
