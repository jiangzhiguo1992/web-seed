# 领域契约（domain）

> 领域层描述**业务上必须成立的事实**：实体不变量、状态转换、业务规则、流程编排、术语。
> 这一层不描述实现，但生成类型、断言与测试骨架；实现必须让这些断言通过。

---

## 1. 文件职责

| 文件 | 内容 | 产物 |
|---|---|---|
| `entities/<entity>.yaml` | 实体、字段语义、不变量、生命周期 | Go/TS 类型、`Validate()` 断言 |
| `states/<machine>.yaml` | 状态、事件、转换、守卫、副作用 | 状态常量、转换表、非法转换测试 |
| `rules/<scope>.yaml` | 业务规则：前置/后置、错误码、正反例 | 规则函数骨架、表驱动测试 |
| `flows/<flow>.yaml` | 业务流程编排（跨能力） | 编排骨架、集成测试骨架 |
| `glossary.md` | 术语表 | 无（review-only） |

## 2. 硬规则

1. **实体字段必须引用 `data.table.*.col.*`**，不重复定义类型与长度。
2. **状态机必须穷举**：每个状态的出边必须全部列出；未列出的转换为非法。
3. **规则必须可执行**：每条规则至少一组 `given/when/then`，否则视为描述而非规则。
4. **流程只编排，不实现**：步骤只引用 `cap.*`，不写具体调用代码。
5. **禁止引用 capabilities / features 之外的业务实现**；domain 只依赖 data 与 platform。
6. **术语表是唯一命名来源**：代码、契约、UI 文案的术语必须与 `glossary.md` 一致。

## 3. 引用方向

```
domain → data（枚举、表字段）
domain → platform（错误码、权限点、事件）
```

反向引用（capabilities / features → domain）由上层发起，domain 不感知调用方。

## 4. 与 features 的区别

| | `domain/flows/*` | `features/flows/*` |
|---|---|---|
| 关注点 | 业务编排（系统视角） | 用户旅程（界面视角） |
| 例子 | 发布笔记 → 写库 → 发事件 → 通知 | 填写表单 → 提交 → 跳转详情 |
| 消费者 | api / worker | web |
